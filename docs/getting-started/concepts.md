# Concepts and glossary

These are the core ideas the rest of the OneTest TMS docs rely on. Skim them once; come back when a
term is unfamiliar.

## The big picture: provider and consumer

OneTest TMS is the **provider** — it stores and tracks your tests on GitHub (cases, runs,
executions, results, reports, coverage). Your **test executor** is the **consumer** — it actually
runs the tests (for example a browser agent driving Playwright) and hands results back to OneTest
TMS.

In plain terms: **OneTest TMS keeps the records; your executor does the work.** They are separate.
You drive both from your agent — the executor performs the steps and captures evidence, then your
agent calls `record_result` to write the outcome into OneTest TMS.

## Glossary

### Organization
The GitHub org that owns your test-management repos and the shared **QA Runs** board.

### Test-management repo (TM repo / product)
The GitHub repo that holds one product's testing assets: the `.onetest/` config, the `tests/` tree,
and the `reports/`. Each product gets its own TM repo (for example `onetest-ai/tm-shop`). Most MCP
tools take an optional `repo` (`OWNER/NAME`) naming the TM repo to operate on; pass the **product**
repo, never a template.

### Test case
A single Markdown file with YAML front-matter under `tests/`, for example
`tests/cart/SHOP-0001_add-to-cart.md`. The front-matter carries fields like `id`, `title`,
`priority`, `type`, `module`, `status`, `execution_type`, `size`, `targets`, `automation_test_id`,
`requirements`, and `tags`; the body holds Preconditions, Test Data, a Steps table, Expected Final
State, and Teardown. URLs use `{{base_url}}` so cases stay environment-agnostic. See
[test-case format](../reference/test-case-format.md).

### Case id
A case's permanent identity: `<SOURCE_KEY>-NNNN`, e.g. `SHOP-0001`. The `SOURCE_KEY` comes from the
TM repo's `.onetest/config.yml`. Ids are allocated automatically and are **immutable — never
reused**.

### Folder / Suite
The folder tree under `tests/` **is** the suite structure. A folder is a suite; subfolders are
sub-suites. You can scope runs and searches by folder.

### Dynamic OQL suite
A folder can contain a `_suite.yml` with `dynamic: true` and an `oql:` query. Its membership is
computed on demand from the query rather than stored as a fixed list:

```yaml
# tests/regression/_suite.yml
dynamic: true
oql: "tags CONTAINS 'regression' AND status = 'ready'"
```

### Tag
A free-form label in a case's front-matter `tags[]` (for example `smoke`, `login`). Tags are a
common way to scope runs via OQL (`tags CONTAINS 'smoke'`).

### Test run
A planned execution of a set of cases. In GitHub it is a **Test Run** Issue in the TM repo, tracked
on the QA Runs board. It is created with `create_run` and closed with `complete_run`.

### Run id
A run's human-readable identity: `RUN-<SOURCE_KEY>-YYYY-MM-DD-NNN`, e.g.
`RUN-SHOP-2026-05-29-001` (a per-day sequence). The underlying GitHub Issue number is the system id.

### Execution
One case's instance within a run — a **Test Execution** Issue created in that case's target repo and
linked to the run Issue as a sub-issue. You reference an execution as `OWNER/REPO#N`, e.g.
`onetest-ai/tm-shop#4`. Results are recorded per execution.

### Result / Status
The outcome of an execution, tracked as the single-select **Result** field on the QA Runs board:

| Status | Meaning |
| --- | --- |
| `not_run` | Created, not yet started |
| `in_progress` | Being executed |
| `passed` | Verified pass (requires evidence) |
| `failed` | Did not meet expected result |
| `blocked` | Could not be executed (dependency/environment) |
| `skipped` | Intentionally not executed |

When recording, your agent passes `PASS | FAIL | BLOCKED | SKIPPED` to `record_result`, which maps
to these statuses. Always record through the tool so the Project field and Issue labels stay in
sync.

### Evidence
A screenshot or log that confirms an execution's outcome, committed to the TM repo under
`reports/<run>/screenshots/` and linked from the Issue. **A PASS is invalid without an evidence
reference** — `record_result` rejects `PASS` with no evidence.

### Failure reason
A classification on a failed/blocked execution, drawn from a fixed list: `bug_in_app`,
`test_data_issue`, `environment_issue`, `test_needs_update`, `blocked_by_other`, `other`. It drives
the "failures by reason" breakdown in reports.

### Defect
A bug filed for a failure — an Issue labeled `defect` in the target repo, cross-referenced from the
failing execution. Create one with `create_defect`, or inline by passing `defect` to
`record_result`. Severity defaults from the case's priority.

### Report
A run's results rolled up into Markdown, committed to `reports/RUN-….md` in the TM repo and linked
from the run Issue. Generated by `complete_run`. Reports include pass rate (`passed / total`),
completion, failures by reason, and per-case metrics. See
[reports and coverage](../guides/reports-and-coverage.md).

### Board (GitHub Project)
The org **QA Runs** Project — the shared board where every run and execution appears. The testing
team works from it: filter by run, see assignees, watch status, and use Insights. It carries fields
like Result, Run, Case, Target, Priority, Size, and Failure reason.

### Target repo
The GitHub repo a case is exercised against — where its execution Issues and defects are created. A
case sets its `targets[]` in front-matter; otherwise the run's `target` or the repo's
`default_targets` applies. If none is set, executions are created in the TM repo itself
(centralized-QA mode).

### Environment
The deployment a run targets (for example `staging` or `production`), defined in
`.onetest/config.yml`. The environment resolves `{{base_url}}` in case steps at run time. Pass it as
`env` to `create_run`.

### Automation coverage
A report of how well your cases are automated: how many are marked automated
(`execution_type: automated`), how many are actually linked to CI results, and where the gaps are.
Produced by `automation_coverage`, after `ingest_results` and `correlate_results` bring automated
results in and match them to cases by `automation_test_id ⇄ code_ref`. See
[automated results](../guides/automated-results.md).

### OQL
The query language for selecting cases — used to scope runs, search, and define dynamic suites. It
matches case fields with operators like `=`, `~`, `IN (...)`, and `CONTAINS`, joined with
`AND`/`OR`/`NOT`. Example: `tags CONTAINS 'smoke' AND priority IN (critical, high)`. See
[OQL reference](../reference/oql.md).
